## Purpose and boundaries

A per-user Windows Known Folders configurator with graphical and CLI entry points, Windows-default reset, exact backup restore and separately approved copy/merge. It does not install iCloud, configure synchronization, automatically migrate files or modify unrelated profile entries.

The [repository layout and development workflow](DEVELOPMENT.md), [CLI reference](CLI.md), and [measured verification history](VERIFICATION.md) are separate documents. Keep architecture decisions here and historical test evidence in verification.

Release-policy parsing consumes the leading BOM preserved by git show and identifies legacy array format before pipeline unwrapping. The cross-shell release-input suite checks native/legacy policy equivalence and rejection of unsafe or duplicate paths.

The native WinUI 3 migration is in ui/ICloudFolderSetup. Its [review decisions, measured coverage and remaining gates](WINUI.md) are tracked separately. tools/Invoke-WinUIBridge.ps1 reuses Get-SetupRequest and existing backends, transports structured progress/results, and preserves direct error output for friendly classification. Native installation uses the same verified per-user installer. Folder, backup and result dialogs use Microsoft.Windows.Storage.Pickers associated directly with AppWindow.Id, with contextual titles/actions and JSON/text filters. Saving a result reports the destination after the write completes. Development Explorer entry points now launch NativeUI/ICloudFolderSetup.exe in setup, reset, check or install mode; an incomplete payload produces an actionable startup error. Published older releases remain unchanged.

Native control accents follow Windows through the standard AccentButtonStyle and selection resources. Decorative identity combines cloud blue and a theme-adjusted system accent; text stays on system foreground brushes. Light, dark and HighContrast dictionaries remain separate, with high contrast delegating identity colors to system window/text resources. Theme fixtures change only the app's requested theme, not Windows personalization settings. The heading and instructions scroll with form content so enlarged text cannot displace the pinned commands. Narrow windows put the primary action on its own full-width row, and the identity caption wraps within a constrained grid column.

## Folder and registry decisions

- Get-FolderMap is authoritative for canonical entries and aliases. Pictures maps to Pictures; old Images content is not automatically merged. Music is optional for iCloud setup; reset includes it. No OneDrive-specific or unrelated entries are modified.
- Get-ICloudFolderDefinitions exposes the seven logical names/relative paths from that map for native display; the UI does not define a second mapping. The default view shows icons and destination paths before preview. Opt-in per-folder editors/pickers serialize an immutable sorted path snapshot through the bridge. Get-FolderMap normalizes overrides, keeps aliases identical, rejects unknown/disabled-Music keys, paths outside the selected root, duplicate targets and overlapping logical folders (Captures may be beneath Videos). Setup, copy and diagnostics use this same target map. Reset/restore refuse overrides. Changing paths or returning to defaults invalidates reviewed approval. Advanced entries are retained while switching modes, but the default mode always uses the standard map.
- New values are normalized absolute REG_EXPAND_SZ strings. Existing types and unexpanded strings are preserved exactly in backups; unsupported original types abort.
- SyncRootManager iCloudDrive registrations validate the current account's active root. A known mismatch cannot be overridden. Manual verification is a fallback only if no registration exists; registration never proves sync health.
- Reset uses Get-FolderMap with SystemDefaults. Canonical Known Folder IDs are defined alongside the mapping. SHGetKnownFolderPath flags 0x4600 request defaults independently of current/parent redirection without creating absent directories. Allocations are freed even on error; failed queries have no guessed fallback.
- Historical backups are never needed for reset. Every apply/reset/restore still creates a fresh exact recovery record.
- The checked registry backend remains intentional. The isolated SHSetKnownFolderPath experiment changed both User Shell Folders and Shell Folders, but a seeded local Documents alias did not follow. Replacing the backend would require separate alias handling and a larger backup/verification surface. See verification for the measured results.

## Settings-change flow

1. Acquire the account mutex and snapshot current values without expansion.
2. Validate destinations, source content, recovery location and complete plan.
3. Return for preview, or enforce apply conditions and ShouldProcess.
4. Write, parse, validate and compare an account-bound exact backup.
5. Probe destination access and compare the snapshot again before writes.
6. Write/check every desired value and the complete set. On failure, restore/check all original values, including deletion of values originally absent.

Recovery storage must not overlap source/destination trees. Manual restore accepts only the mapped allowlist and current SID, requires original destinations to be available, and makes a fresh backup of current settings. No file movement or directory deletion is part of settings changes. Crash/power-loss recovery is manual. Other applications can still change settings; the mutex is not an OS-wide registry transaction.

## Graphical flow and installation

Get-SetupRequest maps controls to existing scripts without duplicating registry logic. Encoded data passes user paths as data to a hidden child process. Output is read asynchronously; closing is blocked while running. Apply requires a matching successful preview/dry run and an action-specific confirmation with Cancel as the default. Option changes invalidate preview. The backend remains responsible for ShouldProcess and safety checks.

The optional installer copies only manifest/central-release-listed files into a unique per-user version directory. It captures validated source hashes during preflight and checks installed copies against those exact hashes before shortcut creation, so a source change during copying cannot become the new expected content. It preserves old binaries and backs up same-name shortcuts. A failed copy can leave an unlinked partial installation directory for inspection. It never redirects folders or installs iCloud. Portable execution and the legacy console wrapper remain supported.

## Explicit copy/merge

Get-CopyPairs reuses the core mapping/value reads, deduplicates alias pairs and validates registration/default destinations. Copy uses the same account mutex but never writes registry settings.

Preview hashes contents. Apply rebuilds the plan, checks paths and source/destination hashes, uses File.Copy with overwrite disabled, and verifies new contents. Identical files are skipped. Conflicting aliases or filenames, file/folder obstructions, overlap, encryption and unsupported reparse points stop the operation. Ancestors are checked; native tag lookup permits Windows Cloud Files placeholders while refusing junctions/symbolic links. Reading placeholders may hydrate content.

Sources are always retained. Partial destination copies remain on failure for inspection; no deletion-based rollback is attempted. This is not a metadata-complete backup or an application-consistent snapshot. A live probe verified copy/hash behavior for a fully local iCloud placeholder; online-only hydration remains outside current evidence.

### Highest-value changes within the current architecture

1. **Implemented: compare plan fields instead of complete JSON strings.** Test-CopyPlansEqual checks counts, ordering and all five fields directly. Text uses ordinal equality, conservatively rejecting case/Unicode spelling changes and distinguishing null from empty hashes. The fresh plan is still rebuilt before writes, then its reference is released after comparison. The file count uses a loop instead of allocating a filtered array. Regression fixtures cover actual source additions/changes/removals/renames and destinations becoming identical between passes, plus order/null/Unicode identity, existing alias/conflict/cancellation behavior and retention of originals. Both full plans still coexist during comparison; a streaming redesign is a separate step.
2. **Bound output end to end.** Invoke-WinUIBridge.ps1 captures complete formatted output with Out-String, collects stderr in StringWriter, appends strings and JSON-escapes the result into one protocol line. BackendClient then reads the entire line and stderr; MainWindow retains full raw and friendly copies and displays the full text. Use versioned structured summaries and bounded chunks, and expose the full plan through paging/on-demand recomputation. Account-private detail files are an option only for explicitly write-enabled operations; do not silently add file writes to read-only Preview or WhatIf. Keep critical errors, recovery paths and approval identity available independently of truncated display text. A bounded producer alone does not bound a consumer that concatenates every chunk again.
3. **Reduce planner retention.** Get-CopyPlan retains a breadth-first queue, a destination-index hashtable and every plan entry, while @(Get-ChildItem ...) additionally materializes a whole directory. Prefer lazy, non-recursive directory enumeration with bounded traversal state and correctly disposed enumerators. This alone does not remove the O(N) plan/index costs. For explicitly approved execution, compact records plus a disk-backed collision index or external sort can provide a strict RAM bound; validate the complete manifest before the first destination write. Read-only Preview/WhatIf must remain write-free. Bounding their global duplicate detection may require slower repeated scans; introducing a preview cache would be a separate documented behavior change, not a transparent optimization. Preserve empty directories, aliases, case rules, complete conflict detection and per-file race checks. Never start copying while later conflicts are still undiscovered.
4. **Avoid launching PowerShell just for startup metadata.** Generate a small metadata resource from Get-ICloudFolderDefinitions during the immutable build and verify/include it in release inputs. Get-FolderMap remains authoritative; do not hand-maintain a second map. This removes the observed metadata-worker startup peak rather than merely hiding it behind asynchronous UI loading.
5. **Coalesce progress and reduce transient allocations.** Native progress currently queues one dispatcher callback per event; the compatibility reader also stores every line in a queue and a StringBuilder. Retain the latest progress state and update at a bounded cadence, independent of per-file cancellation checks. Count files without a filtered temporary array, use compact typed records where practical, and avoid repeated provider-object construction in path validation. Path/reparse validation immediately before writes must remain current; caching must not bypass those checks.
6. **Reject oversized input before full parsing.** Backup, cloud-state and installation-manifest readers use whole-file Get-Content/ConvertFrom-Json before validating shape. Define byte, record-count, nesting and string bounds from the supported schemas/path lengths, then enforce them before allocation. Keep exact backup round-trip/readback validation; ordinary backups contain at most thirteen managed values, so optimizing those small arrays is low priority.

### Extreme memory target

The bare-worker measurement already exceeds a 4 MiB whole-process budget. PowerShell tuning can reduce peaks but does not establish a route to that budget. A native backend would need to replace the interpreter/runtime as well as its work: fixed-schema requests and exact backup serialization, Windows registry/known-folder calls, bounded directory traversal, streamed SHA-256, non-overwriting copying, a compact reviewed-plan manifest and explicit rollback. Use binary 32-byte hashes internally and shared path prefixes/relative names where appropriate; format full paths and hexadecimal hashes only for display. Reuse the safety contract/fake-registry scenarios and guarded integration matrix against the replacement before switching launchers.

The existing file-content path is already a good starting point: Get-FileHash is stream-capable, and [IO.File]::Copy does not explicitly read a whole file into a PowerShell byte array. The 1/64 MiB hash fixtures showed essentially flat worker memory. Avoid replacing this with ReadAllBytes, removing verification, retaining a permanent PowerShell pool, or using forced GC/working-set trimming to make benchmark numbers look smaller. Registry/mutex/stream handles are generally disposed already; nested Shell namespace/Self COM objects and repeated Shell.Application activation deserve a smaller follow-up lifetime review. Installer manifest lookups can be indexed once instead of filtering every entry repeatedly, primarily to reduce CPU and allocation churn.

References: [stream-capable Get-FileHash](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/get-filehash?view=powershell-5.1), [incremental filesystem enumeration](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/file-system/how-to-iterate-through-a-directory-tree), and [SHA-256 stream APIs](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.sha256). These document available mechanisms, not the measured footprint of a future implementation.

### Replacement-backend research (2026-10-24)

The strongest candidates for the extreme memory target are C++ calling Win32 directly and Rust with narrow Windows bindings. This is an architectural assessment; neither replacement has been implemented or measured against the 4 MiB budget.

| Candidate | Fit and trade-off |
| --- | --- |
| C++ with Windows SDK | Direct access to registry, shell, files and cryptography; explicit allocation and RAII handle ownership. Strong candidate when minimal dependencies and direct SDK integration lead. Buffer, ownership and error-path correctness require careful review. |
| Rust with Windows bindings | Ownership-based cleanup without tracing GC; put Windows FFI in small reviewed wrappers. Strong candidate when memory safety and maintainable parsing/plan logic lead. Prefer focused or generated bindings where appropriate and pin their versions; raw bindings do not provide handle ownership automatically. |
| C with Windows SDK | Direct allocation control and a small implementation are possible. More manual ownership/error cleanup than C++ or Rust; not the default choice for this backup/rollback-heavy application. |
| C# NativeAOT | Directly reusable .NET concepts and no runtime JIT; still includes required runtime libraries. A practical lower-friction option to benchmark if the strict budget is relaxed. It does not compile away a hosted PowerShell engine. |
| Zig | Explicit allocators and no hidden language-level allocation. A viable experiment, with Windows binding/resource handling and toolchain compatibility needing a separate prototype. |
| Go | Capable of implementing the operations, but its GC/runtime and soft memory limit make it a lower-priority choice for a strict whole-process budget. The memory limit is not a Windows process working-set cap. |

All candidates must port the actual backend, not wrap powershell.exe. Keep the UI choice independent: the existing WinUI client can initially launch a short-lived native worker over a versioned, bounded protocol. Retain PowerShell for tests/build orchestration and compatibility wrappers if useful; production operations must not start it when measuring a PowerShell-free runtime. No permanent service, generic scripting engine, async executor or thread pool is required for the current serial operation model. A native DLL can be considered later, after the isolated executable is correct and measured.

The required primitives already exist in Windows: registry query/set/delete APIs preserve types and absence; SHGetKnownFolderPath retrieves defaults/current locations; incremental enumeration and reparse-tag checks implement guarded traversal; BCryptHashData accepts successive buffers for streamed SHA-256; CopyFileExW can refuse an existing destination. These APIs supply mechanisms, not application-level exact backup/rollback or approval semantics. In particular, CopyFileEx cancellation can delete a partial destination, while PROGRESS_STOP retains it: preserve the existing finish-and-verify-current-file cancellation contract instead of adopting different defaults. Keep the same registration, alias, no-overwrite, encrypted/reparse-point and source-retention rules.

A useful first gate is a read-only native worker implementing metadata, configuration checks and fixture copy-plan hashing. Measure its sampled process peaks, private bytes, handle counts and output size with the same fixtures as the PowerShell baseline. Port exact backup/restore and checked writes only after fixture parity; real writes remain restricted to guarded disposable hosted Windows/Sandbox. Preserve the backup schema or provide explicit tested compatibility, including originally absent values. During migration there must be one authoritative mapping used/generated by both implementations; a native map becomes authoritative only at a deliberate cutover. A 4 MiB claim requires representative operations and loaded Windows-library pages, not just an empty process or a small EXE.

Sources: [Rust ownership](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html), [Windows Rust binding guidance](https://github.com/microsoft/windows-rs), [NativeAOT limitations/runtime libraries](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/), [Zig allocation model](https://ziglang.org/learn/overview/), [Go GC and soft memory limits](https://go.dev/doc/gc-guide), [registry APIs](https://learn.microsoft.com/en-us/windows/win32/sysinfo/registry-functions), [Known Folders](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/nf-shlobj_core-shgetknownfolderpath), [incremental BCrypt hashing](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcrypthashdata), and [CopyFileExW semantics](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-copyfileexw).

These are small-process baselines, not equivalent implementations of this backend. Three sequential runs per case used a verified hidden desktop, no console window, and external 20 ms sampling. Total ranges cover both sampling passes; private-working-set ranges come from the second pass. They are different from private committed memory: for example, the native API probe committed about 1.6 MiB privately while its private resident peak was about 1.1 MiB. Shared DLL pages contribute to total resident working set. A 4 MiB private-resident goal and a 4 MiB total-resident goal therefore have materially different feasibility. Do not silently switch metrics to meet a target.

The native probe reads the existing Desktop registry value, hashes a 64 KiB heap buffer in sixteen chunks, and queries the Windows-supplied Desktop default with non-creating flags. It performs no registry writes, directory creation, file copies or redirection. It is not a full backup/parser/copy engine. Both read-only registry and default-path calls succeeded in the unrestricted hidden-desktop run, unlike the earlier restricted default-query fixture. The special no_std/no-CRT build is not a benchmark of a typical Rust application. Ordinary Rust and NativeAOT builds could not be completed with the currently installed linker libraries; other candidate compilers were unavailable. No compiler installations were performed.

For choosing prototypes only, a conservative provisional planning envelope for a small worker loading equivalent Windows APIs is roughly 10-20 MiB total working set for C/C++, ordinary Rust, Zig, Odin, D BetterC or Free Pascal; roughly 10-25 MiB for Nim or an embedded Lua/LuaJIT/QuickJS worker; roughly 15-40 MiB for C# NativeAOT or Go; and roughly 10-30 MiB for AutoIt. These are low-confidence engineering budget placeholders inferred from architecture and the measured native probe, not measured language results or published benchmark ranges. They are deliberately broad/overlapping, are not upper bounds, and do not apply to an unbounded in-memory copy plan. A fair language ranking needs the same API set, parsing, output and fixture workload built for each candidate. CMD's measured number excludes helpers such as reg.exe or hashing tools, which must be counted in a real batch backend.

No vendor RAM guarantee was found for the requested complete backend.
