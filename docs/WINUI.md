# Native UI migration

## Decision and boundaries

The new interface uses C# and WinUI 3 from the stable Windows App SDK 2.5.1, targeting .NET 10 and an unpackaged, self-contained distribution. This keeps the existing portable-folder and per-user installation model. global.json pins .NET SDK 10.0.402. Package dependencies and both x64/ARM64 runtime targets are pinned in the project and packages.lock.json; ui/NuGet.Config uses the official NuGet feed. No machine-wide runtime or Developer Mode change is required by this deployment model.

The currently published older release still uses Windows Forms. Development Explorer launchers now target the self-contained NativeUI payload; setup/reset/check remain preview-first, and install opens the native Cancel-default confirmation. The migration is not a new published release.

## Build and test

From the repository root, with the .NET 10 SDK installed:

~~~powershell
dotnet build .\ui\ICloudFolderSetup\ICloudFolderSetup.csproj -c Debug -p:Platform=x64 -p:RestoreLockedMode=true
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\Test-WinUI.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\Test-WinUITheme.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\Test-WinUILayout.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\Test-WinUIAccessibility.ps1
dotnet build .\ui\ICloudFolderSetup\ICloudFolderSetup.csproj -c Release -p:Platform=x64 -p:RestoreLockedMode=true
~~~

Test-WinUI.ps1 automatically uses the verified hidden-desktop runner. Its backend and installation scripts are isolated fixtures. The copy portion uses the real copy module with fixture source/destination pairs. It never applies folder settings or creates shortcuts in the developer's actual Start menu or Desktop. The Debug-only rendering switch is absent from Release builds. Images and logs stay beneath ignored .local/hidden-desktop.

Test-WinUITheme.ps1 changes only the app fixture's requested theme. It checks actual light/dark brush values against Windows UISettings and emits palette reports beside the rendered images; it never changes the user's Windows theme or accent. The high-contrast resource check is structural, with actual OS contrast-theme transitions still unverified. ARM64 Release cross-compilation passes locally; that is not evidence of running the native app on ARM64 hardware.

The configured native-ui CI job builds locked Debug/Release source, runs the native behavior, theme and layout hidden-desktop suites, cross-builds ARM64, and retains fixture evidence. Hosted run 39943986391 passed native Debug/Release x64 builds and all behavior, theme, layout and accessibility fixtures. Its high-contrast helper failed with heap corruption; that helper is being corrected, and hosted ARM64/package gates remain pending.

Test-WinUILayout.ps1 renders the actual native window at 960 x 800, 640 x 720 and 480 x 640 logical pixels on the hidden desktop. Debug-only measurements verify all nine action variants: command buttons stay inside the client area without overlap, read-only actions hide mutation controls, and action-specific path rows remain horizontally contained. All 54 cases pass locally, with the narrow enlarged cloud view visually inspected. The expanded matrix uses normal and doubled rendered font sizes across all nine actions and three widths. It checks a usable scroll viewport, command containment/non-overlap and actual narrow-window primary-action reflow; the renderer refuses empty frames. Font sizes are snapped before applying the fixture multiplier so inherited sizes are not multiplied repeatedly. These are app-local stress fixtures, not changes to Windows text scaling or evidence of physical monitor transitions. CI includes this suite; hosted execution remains pending.

## Remaining release gates

Test-WinUIPickers.ps1 is guarded before UI startup and runs only in disposable Windows. It exercises the actual desktop-specific Windows App SDK dialogs: cancel and select a Unicode folder, cancel and select a JSON backup without enabling Apply, then cancel and save exact displayed result text. Pickers must be owned by the native process and visible to automation on its verified hidden desktop. The UI Automation client runs in a standalone .NET Framework console driver: Win32 provider registration fails in PowerShell's native host but succeeds with a managed entry point. The driver compiles and its provider-only probe passes locally; it never opens dialogs in that probe mode. Hosted run 39982378929 passed folder cancellation and Unicode selection; backup cancellation timed out. The driver now identifies button-role controls explicitly and checks dismissal using dialog visibility plus the owner enabled state, allowing a dismissed common dialog to retain its HWND. Full backup/save interaction still needs hosted verification. See [Microsoft's desktop picker guidance](https://learn.microsoft.com/windows/apps/develop/files/using-file-folder-pickers).

The contrast query helper follows .NET's ownership rule for the Windows-owned scheme pointer. The HIGHCONTRASTW documentation incorrectly advises freeing it; the resulting heap corruption occurred after a hosted toggle followed by another query. Test-ContrastQuery.ps1 now performs twenty read-only queries on a hidden desktop and passes locally. See the explicit ownership correction in [.NET's interop implementation](https://source.dot.net/System.Private.Windows.Core/Windows/Win32/PInvokeCore.SystemParametersInfo.cs.html). Actual toggling remains restricted to disposable environments.

Test-WinUIHighContrast.ps1 is a disposable-environment-only gate. Assert-IsolatedEnvironment.ps1 runs before UI initialization or any settings API call. Inside the verified hidden desktop it captures Windows high-contrast flags/scheme, enables contrast using SystemParametersInfoW, requires the native app to observe contrast mode, compares both identity colors with Windows window-text color, then restores and reads back the original flags/scheme in finally. It reruns theme rendering after restoration. A hidden desktop alone does not isolate account-wide personalization. Local evidence covers helper compilation, developer-account refusal and unchanged normal-theme regressions; Hosted run 39947657439 successfully rendered and checked both contrast-mode palettes after the real toggle. Run 39982378929 additionally verified exact flag restoration and matching original Light/Dark palettes. Windows initialized the initially empty inactive scheme name to High Contrast Black. The revised assertion allows only initialization of an empty name while contrast was originally off; all flags, original palettes and any pre-existing scheme name must still match exactly. This revised gate needs hosted verification. See [Microsoft's HIGHCONTRAST contract](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-highcontrastw).

Test-WinUIAccessibility.ps1 exercises native FocusManager forward/reverse tab-order navigation through the setup form, including expanded advanced options. It checks actual automation-peer names/roles/help text, the reverse sequence and exclusion of disabled Apply. Advanced-option help includes the non-overridable mismatch restriction and retained-files guidance. The fixture restores the last control before the backward pass because the scoped forward search can hand focus to the host at the boundary. It invokes no actions and sends no physical keyboard input. See [Microsoft's focus-navigation API](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.input.focusmanager.trymovefocus). This does not verify navigation-menu arrow keys, access-key activation, spoken Narrator output or real key delivery. Theme/layout report cleanup explicitly removes the JSON sidecar before every run so an older report cannot satisfy a new test.

- Verify native file pickers and remaining error states. Normal/doubled-font layout fixtures pass for all nine actions at all three widths. The native heading now scrolls with content and primary actions reflow from actual client width. The hosted shell matrix and all three guarded real-registry/API jobs passed in run 39944837536; the overall native/package gate is still incomplete.
- Complete keyboard, accessible-state/focus, theme, high-contrast and DPI coverage with honest evidence boundaries.
- Run hosted Windows/ARM64 builds and guarded integration gates. Local native WhatIf/reinstall, exact shortcut backup, modified-DLL and missing-PRI rejection checks pass. Local reproducibility, checksum, traversal and unavailable-certificate checks pass.
- Keep the original index/main state intact while using the alternate-index validation branch. Resolve final main integration without including the pre-existing mass staged deletion.

## Native package evidence (local, 2026-10-23)

A source-snapshot x64 package containing 545 files passed checksum, complete manifest, syntax, apphost/WinUI PE architecture and dependency-target verification. The app PRI is explicitly included through a project target because the unpackaged MRT Core build path omits it from publish items by default; see [Microsoft's tracked issue](https://github.com/microsoft/WindowsAppSDK/issues/6720). Compiler intermediates and package-test fixtures use temporary storage outside iCloud Drive.

On a verified hidden desktop, the actual extracted archive's setup/reset/check/install launchers started the native Release app. Mutation actions began disabled, and installation confirmation was cancelled. A real fixture installation then hash-verified the entire runtime, created fixture-only native shortcuts, and successfully launched the installed checker. No developer-account folder settings or real Start menu/Desktop shortcuts were changed. Two unsigned builds were byte-identical; changed checksums, unsafe archive paths and unavailable signing certificates were rejected. The new verifier also accepted the immutable published v2.3.1 legacy archive. Source snapshots use an alternate Git index; current source is on the separate validation branch, with no new published release. The original index state is preserved.
