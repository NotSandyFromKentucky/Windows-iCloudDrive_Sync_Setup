# Native UI migration

## Decision and boundaries

The new interface uses C# and WinUI 3 from the stable Windows App SDK 2.5.1, targeting .NET 10 and an unpackaged, self-contained distribution. This keeps the existing portable-folder and per-user installation model. global.json pins .NET SDK 10.0.402. Package dependencies and both x64/ARM64 runtime targets are pinned in the project and packages.lock.json; ui/NuGet.Config uses the official NuGet feed. No machine-wide runtime or Developer Mode change is required by this deployment model.

The v2.3.1 release archives use Windows Forms. The v2.4.0 Explorer launchers target the self-contained NativeUI payload; setup/reset/check remain preview-first, and install opens the native Cancel-default confirmation. The release workflow publishes new versioned archives and never replaces older assets.

## Build and test

From the repository root, with the .NET 10 SDK installed:

~~~powershell
dotnet build .\ui\ICloudFolderSetup\ICloudFolderSetup.csproj -c Debug -p:Platform=x64 -p:RestoreLockedMode=true
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\Test-WinUI.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\Test-WinUITheme.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\Test-WinUILayout.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tests\Test-WinUIAccessibility.ps1
dotnet build .\ui\ICloudFolderSetup\ICloudFolderSetup.csproj -c Release -p:Platform=x64 -p:RestoreLockedMode=true
~~~

Test-WinUI.ps1 automatically uses the verified hidden-desktop runner. Its backend and installation scripts are isolated fixtures. The copy portion uses the real copy module with fixture source/destination pairs. It never applies folder settings or creates shortcuts in the developer's actual Start menu or Desktop. The Debug-only rendering switch is absent from Release builds. Images and logs stay beneath ignored .local/hidden-desktop.

Test-WinUITheme.ps1 changes only the app fixture's requested theme. It checks actual light/dark brush values against Windows UISettings and emits palette reports beside the rendered images; it never changes the user's Windows theme or accent. This suite does not toggle Windows contrast; the separate guarded contrast suite passed a real hosted toggle and restoration in run 39998473905. ARM64 Release cross-compilation passes locally; that is not evidence of running the native app on ARM64 hardware.

The native-ui CI job builds locked Debug/Release source, runs native behavior/theme/layout/accessibility suites, tests actual contrast and owned pickers in a guarded disposable VM, cross-builds ARM64, and retains fixture evidence. [Hosted run 40002408818](https://github.com/NotSandyFromKentucky/Windows-iCloudDrive_Sync_Setup/actions/runs/40002408818), source 5ab9f356b81867c5471383ca9671dab11ee19ddf, passed all eleven jobs: six shell combinations, three guarded integration images, native UI and immutable package verification.

Test-WinUILayout.ps1 renders the actual native window at 960 x 800, 640 x 720 and 480 x 640 logical pixels on the hidden desktop. Debug-only measurements verify all nine action variants: command buttons stay inside the client area without overlap, read-only actions hide mutation controls, and action-specific path rows remain horizontally contained. The original 54 cases plus six advanced-folder cases (all three widths, normal/doubled text) pass locally. Destination paths/editors/pickers are checked for horizontal containment, and the compact default view was visually reviewed. The expanded matrix uses normal and doubled rendered font sizes across all nine actions and three widths. It checks a usable scroll viewport, command containment/non-overlap and actual narrow-window primary-action reflow; the renderer refuses empty frames. Font sizes are snapped before applying the fixture multiplier so inherited sizes are not multiplied repeatedly. These are app-local stress fixtures, not changes to Windows text scaling or evidence of physical monitor transitions. All 54 cases also passed in hosted run 39998473905.

## Default and advanced destinations

### UI review and performance baseline (2026-10-24)

Review references: Microsoft's [responsive UI guidance](https://learn.microsoft.com/en-us/windows/apps/develop/performance/keep-ui-thread-responsive), [Windows app best practices](https://learn.microsoft.com/en-us/windows/apps/get-started/best-practices), and [accessibility checklist](https://learn.microsoft.com/en-us/windows/apps/design/accessibility/accessibility-checklist).

- Startup previously blocked the UI thread on the metadata worker. The window now activates before asynchronous loading, displays loading status, and disables actions until the authoritative map arrives. A delayed-worker fixture verifies the window's automation remains responsive and Preview/Apply remain disabled.
- Navigation and folder destinations already use Windows Symbol/Fluent glyphs; retain adjacent text labels and native InfoBar severity icons. Decorative folder glyphs are excluded from the accessibility tree to avoid duplicate announcements. Do not add generated pictograms or rely on color alone.
- Keep the default destination list read-only with TextBlock roles; reveal editable fields only in advanced mode. Retain action-specific confirmation, pinned commands, system theme resources and owned pickers. The full default/advanced feature passed all eleven jobs in [run 40015033918](https://github.com/NotSandyFromKentucky/Windows-iCloudDrive_Sync_Setup/actions/runs/40015033918), commit 677c5a8c5e11fe82ce8c1417ff30fe87ea7fbfb3. This precedes the asynchronous startup change.
- Remaining manual acceptance includes actual Narrator speech, physical keyboard/access-key delivery and transitions between monitors with different DPI. Automated peers, theme and layout fixtures do not certify those experiences.

Measured the extracted unsigned x64 Release UI at commit 677c5a8c5e11fe82ce8c1417ff30fe87ea7fbfb3 on a verified hidden desktop: 179.1 MiB working set, 93.3 MiB private committed memory, 189.8 MiB peak working set. Ten samples at 500 ms intervals after ten seconds idle were stable. The window was discoverable after 3,340 ms in this single run. These are UI-process figures, excluding the transient PowerShell worker, not a cold-start benchmark or an operation-memory bound. Working set includes shared resident pages; private bytes measure committed private memory and are not synonymous with resident RAM. Preserve this as a baseline; do not attribute it to later builds or infer savings without measuring.

The default setup view shows seven logical folders with native Fluent icons and proposed paths, including optional Music. Advanced mode exposes a named textbox and owned folder picker for each destination; unchecked Music stays disabled. Definitions come from Get-FolderMap through a read-only bridge request. Custom options use a sorted immutable JSON snapshot so edits and mode changes invalidate preview approval. Setup, copy and diagnostics share the same validated target map; reset/restore keep their original destinations. Local tests cover custom aliases, preview/WhatIf, invalid scope/overlap, exact rollback/restore, Unicode transport, shared copy/check expectations and default/advanced focus navigation. Each candidate still requires full hosted CI, including the guarded custom picker interaction.

## Acceptance fixtures and evidence boundaries

Test-WinUIPickers.ps1 is guarded before UI startup and runs only in disposable Windows. Hosted run 40002408818 passed actual folder and JSON-backup cancellation/Unicode selection, unreviewed-Apply exclusion, save cancellation, exact saved path/content and completion announcement. The standalone managed UI Automation client registers Win32 providers, selects button-role controls explicitly and checks dialog dismissal by visibility plus owner enablement. Modern save filename edits use character messages sent only to the verified owned child HWND, because ValuePattern can change displayed text without notifying the save dialog's selected-path model. No SendInput or desktop switch is used. See [Microsoft's desktop picker guidance](https://learn.microsoft.com/windows/apps/develop/files/using-file-folder-pickers).

The contrast query helper follows .NET's ownership rule for the Windows-owned scheme pointer. The HIGHCONTRASTW documentation incorrectly advises freeing it; the resulting heap corruption occurred after a hosted toggle followed by another query. Test-ContrastQuery.ps1 now performs twenty read-only queries on a hidden desktop and passes locally. See the explicit ownership correction in [.NET's interop implementation](https://source.dot.net/System.Private.Windows.Core/Windows/Win32/PInvokeCore.SystemParametersInfo.cs.html). Actual toggling remains restricted to disposable environments.

Test-WinUIHighContrast.ps1 is a disposable-environment-only gate. Assert-IsolatedEnvironment.ps1 runs before UI initialization or any settings API call. Inside the verified hidden desktop it captures Windows high-contrast flags/scheme, enables contrast using SystemParametersInfoW, requires the native app to observe contrast mode, compares both identity colors with Windows window-text color, then restores and reads back the original flags/scheme in finally. It reruns theme rendering after restoration. A hidden desktop alone does not isolate account-wide personalization. Local evidence covers helper compilation, developer-account refusal and unchanged normal-theme regressions; Hosted run 39947657439 successfully rendered and checked both contrast-mode palettes after the real toggle. Run 39982378929 additionally verified exact flag restoration and matching original Light/Dark palettes. Windows initialized the initially empty inactive scheme name to High Contrast Black. The revised assertion allows only initialization of an empty name while contrast was originally off; all flags, original palettes and any pre-existing scheme name must still match exactly. Hosted run 39998473905 passed this complete gate. See [Microsoft's HIGHCONTRAST contract](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-highcontrastw).

Test-WinUIAccessibility.ps1 exercises native FocusManager forward/reverse tab-order navigation through the setup form, including expanded advanced options. It checks actual automation-peer names/roles/help text, the reverse sequence and exclusion of disabled Apply. Advanced-option help includes the non-overridable mismatch restriction and retained-files guidance. The fixture restores the last control before the backward pass because the scoped forward search can hand focus to the host at the boundary. It invokes no actions and sends no physical keyboard input. See [Microsoft's focus-navigation API](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.input.focusmanager.trymovefocus). This does not verify navigation-menu arrow keys, access-key activation, spoken Narrator output or real key delivery. Theme/layout report cleanup explicitly removes the JSON sidecar before every run so an older report cannot satisfy a new test.

- Every candidate must pass the complete hosted matrix, guarded integration, native fixtures and immutable package gate before tagging. A native ARM64 cross-build is not a native ARM64 runtime certification.
- UI Automation peers, focus navigation and enlarged-text fixtures do not certify Narrator speech, physical key delivery or physical multi-monitor DPI transitions. Keep these limitations explicit.
- Use the alternate-index validation branch and preserve the original staging state when integrating main; never include the pre-existing mass staged deletion.

Microsoft references: [unpackaged deployment](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app), [WinUI startup guidance](https://learn.microsoft.com/en-us/windows/apps/get-started/start-here), and [Windows App SDK release channels](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-channels).

## Native package evidence (local and hosted, 2026-10-23)

A source-snapshot x64 package containing 545 files passed checksum, complete manifest, syntax, apphost/WinUI PE architecture and dependency-target verification. The app PRI is explicitly included through a project target because the unpackaged MRT Core build path omits it from publish items by default; see [Microsoft's tracked issue](https://github.com/microsoft/WindowsAppSDK/issues/6720). Compiler intermediates and package-test fixtures use temporary storage outside iCloud Drive.

On a verified hidden desktop, the actual extracted archive's setup/reset/check/install launchers started the native Release app. Mutation actions began disabled, and installation confirmation was cancelled. A real fixture installation then hash-verified the entire runtime, created fixture-only native shortcuts, and successfully launched the installed checker. No developer-account folder settings or real Start menu/Desktop shortcuts were changed. Two unsigned builds were byte-identical; changed checksums, unsafe archive paths and unavailable signing certificates were rejected. The new verifier also accepted the immutable published v2.3.1 legacy archive. Source snapshots use an alternate Git index to exclude the pre-existing staged deletions. The original index state is preserved, and no published release has been replaced.

A follow-up Release build with asynchronous startup measured 181.4 MiB working set, 95.2 MiB private bytes and 188.0 MiB peak working set using the same idle sampling method. Window discovery took 3,887 ms while other validation was running. These single runs do not demonstrate a launch-speed or memory reduction; the verified improvement is that delayed metadata loading no longer blocks window rendering/automation. Memory remains approximately 180 MiB resident for the UI alone on this machine.
